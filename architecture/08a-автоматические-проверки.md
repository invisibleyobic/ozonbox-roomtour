## Часть 1. Что защищает процесс работы над репозиторием уже сегодня

Кода продукта нет (`01-что-строим.md`, раздел 7 - «`package.json` отсутствует»). Здесь нет ни одной строки о будущем Next.js-коде - только о том, что уже физически останавливает агента при работе над самим репозиторием.

| Что проверяем | Как запускаем | Ожидаемый результат | Что считаем ошибкой |
|---|---|---|---|
| **Секреты не читаются и не редактируются агентом.** `.env`, `*.pem`, `*.key`, `credentials.json`, `.mcp.json` (кроме `.env.example`/`.env.sample`); значение переменной не печатается | `.claude/hooks/guard.mjs`, событие `PreToolUse` на `Bash`/`PowerShell`/`Read`/`Edit`/`Write`/`MultiEdit`/`NotebookEdit`/`Grep`; `deny` в `.claude/settings.json` для тех же путей | попытка чтения/правки запрещённого файла или печати значения переменной обрывается до выполнения, агент получает отказ | инструмент всё же выполнился и вернул содержимое секретного файла или значение переменной |
| **В git - только поимённо, без обхода проверок.** Запрет `git add .`/`-A`/`--all`/`-u`, `commit -a`, `--no-verify`, `-c core.hooksPath`, `git push --force` | `guard.mjs`, правила `git-add-all`, `git-skip-checks`, `git-force-push` | команда с любым из перечисленных флагов останавливается до выполнения | коммит или пуш с обходом создался фактически |
| **Секреты и приватные пути не попадают в коммит.** `.env*`, `.mcp.json`, `credentials.json`, `*.pem`/`*.key`/`*.dump`/`*.sql.gz`, `.claude/settings.local.json`, каталоги `.business`, `uploads`, `storage`, `exports`, `media-raw`; в содержимом - ключи провайдеров, приватные ключи, JWT, пароль в строке подключения | `.git/hooks/pre-commit` → `python scripts/check_secrets.py --staged`; вручную и по всему индексу - `check_secrets.py --tracked` через `security-audit.sh` | коммит с найденным секретом или запрещённым путём не создаётся, код выхода 1 | коммит создался, хотя индекс содержал секрет или запрещённый путь |
| **База не сбрасывается, данные не удаляются без `WHERE`.** `prisma migrate reset`, `db push --force-reset`/`--accept-data-loss`, `dropdb`, `DROP`/`TRUNCATE`, `DELETE FROM` без `WHERE` | `guard.mjs`, правило `db-reset`, событие `PreToolUse` на Bash/PowerShell | команда останавливается до выполнения | команда со сбросом или неограниченным удалением выполнилась |
| **Защищённые каталоги и обход разрешений.** `rm`/`Remove-Item` по `idea/`, `architecture/`, `.business/`, `.git/`; флаги `--dangerously-skip-permissions`/`bypassPermissions` | `guard.mjs`, правила `protected-dirs`, `bypass-permissions` | команда останавливается до выполнения | защищённый каталог удалён или режим обхода включён |
| **Ручной прогон перед выкатом.** Тесты сканера секретов, тесты `guard.mjs`, `.business/` не в индексе git, секреты по всему индексу | `bash scripts/security-audit.sh`, запускается вручную - ничего не вызывает его автоматически | все четыре шага возвращают ноль | любой из четырёх шагов вернул не ноль |

⚠️ Расхождение, проверенное чтением кода: `guard.mjs` и `settings.json` заодно блокируют `.mcp.json`, хотя в `CLAUDE.md` этот путь отдельно не назван. Билд и линтер стека (`CLAUDE.md`, принцип 7) сегодня физически не существуют - кода нет.

## Часть 2. Нерушимые правила продукта (`00-правила-проекта.md`, «Всегда»)

Пять правил раздела «Всегда делай» - это про сам продукт, не про репозиторий. Здесь для каждого - как оно превращается в проверку.

### 2.1 У каждого заказа есть источник

| | |
|---|---|
| **Что проверяем** | нельзя записать заказ без источника; заказ без данных получает `unknown`, а не пустое поле |
| **Как запускаем** | ограничение `NOT NULL` в `prisma/schema.prisma`; модульный тест `lib/orders/index.test.ts` - вызов `createOrder()` без промокода и без cookie источника |
| **Ожидаемый результат** | запись с пустым `source_platform` база отклоняет; вызов без явного источника создаёт заказ с `source_platform = 'unknown'`, а не падает и не оставляет поле пустым |
| **Что считаем ошибкой** | заказ создан с `NULL`/пустой строкой в поле источника любым путём |

### 2.2 Цены, остатки, тарифы, тексты и текущий сезон - в базе или конфиге, не в коде

| | |
|---|---|
| **Что проверяем** | в JSX/TSX компонентов витрины нет захардкоженных сумм и названий сезона |
| **Как запускаем** | ESLint-правило (`no-restricted-syntax` на литералы вида `\d+\s*₽` и на строки названий сезона вне `lib/season/`) как часть `npm run lint` |
| **Ожидаемый результат** | линтер не находит числовых литералов цен и строковых литералов сезона в `components/` и `app/` |
| **Что считаем ошибкой** | найден литерал - линтер завершает `npm run lint` ненулевым кодом |
| **Проверить нечем полностью** | что цифра на экране пришла именно из базы, а не подсмотрена и вписана совпадающим литералом - линтер ловит только литерал в коде, не источник данных на экране. Это остаётся дисциплиной код-ревью |

### 2.3 Весь текст - HTML поверх видео, сцена работает без видео

| | |
|---|---|
| **Что проверяем** | ни один текстовый узел сцены не находится внутри `<video>`/`<canvas>`; при отключённом видео весь текст сцены виден и читаем |
| **Как запускаем** | снапшот-тест `components/scene/SceneFallback.test.tsx`; сквозной тест Playwright - страница с заблокированным видео (`06-внешние-сервисы.md` уже называет Playwright MCP для разработки, раздел 12.2) |
| **Ожидаемый результат** | заголовок, цена и кнопка присутствуют в DOM и видимы без единого запроса к видеофайлу |
| **Что считаем ошибкой** | при отключённом видео пропадает любой текстовый элемент сцены или кнопка покупки |

### 2.4 Бюджет скорости страницы

| | |
|---|---|
| **Что проверяем** | LCP на мобильном профиле ≤ 2,5 с; видео не входит в критический путь загрузки |
| **Как запускаем** | Lighthouse CI, мобильный профиль, жёсткий gate сборки (`01-что-строим.md`, раздел 6, пункт 8; тот же порог фигурирует в фазе 6 плана реализации) |
| **Ожидаемый результат** | отчёт Lighthouse укладывается в порог на каждой странице сцены и каталога |
| **Что считаем ошибкой** | LCP выше 2,5 с на мобильном профиле - сборка не проходит gate |
| **Открыто** | ⚠️ где именно живёт конфиг Lighthouse (`lighthouserc.json` в корне или воркфлоу CI) - решается вместе с выбором CI-провайдера на этапе кода, не блокирует эту таблицу |

### 2.5 Копейки и идемпотентный вебхук оплаты

| | |
|---|---|
| **Что проверяем** | суммы - целые копейки, не дробные рубли; `итого = товары - выгода + доставка`; выгода не больше суммы товаров; повторный вебхук с тем же `cp_transaction_id` и видом уведомления не создаёт второй платёж; у заказа не может быть больше одного успешного `PAY` |
| **Как запускаем** | тип полей `*_kopecks` - строго `Int` в `prisma/schema.prisma`; `CHECK`-ограничение на равенство сумм; уникальный индекс на паре «`cp_transaction_id` + вид уведомления» и частичная уникальность «не больше одного `PAY` на заказ»; интеграционный тест `app/api/webhooks/cloudpayments/route.test.ts` - вызов обработчика дважды одним и тем же телом; логика округления и денег - `lib/orders/money.test.ts` |
| **Ожидаемый результат** | запись с нарушенным равенством или отрицательной суммой отклоняется constraint-ом; двойной вызов вебхука создаёт ровно одну строку в `payments`, заказ переходит в `PAID` ровно один раз |
| **Что считаем ошибкой** | тип поля не `Int`; вставка с неверным равенством прошла; повторный вебхук создал вторую запись платежа или второй раз перевёл заказ в `PAID` |

### 2.6 Запрещено: удаление только мягкое

| | |
|---|---|
| **Что проверяем** | `orders`, `order_items`, `payments` не удаляются физически ни при каком пути кода продукта; стирание персональных данных - это `UPDATE` четырёх полей, а не `DELETE` строки |
| **Как запускаем** | в `lib/orders/` нет экспортированной функции удаления заказа целиком; тест `lib/orders/erasePersonalData.test.ts` проверяет, что после вызова строка заказа остаётся, меняются только `customer_name`/`customer_phone`/`customer_email`/`address_line`/`personal_data_erased_at` |
| **Ожидаемый результат** | после стирания заказ находится по `id`, суммы, состав и источник не изменились |
| **Что считаем ошибкой** | строка заказа физически исчезла из таблицы либо стёрлось поле, не входящее в список четырёх контактных |

## Часть 3. Права и денежные потолки (`07-безопасность.md`)

### 3.1 Права агента-разработчика

Технические ограничения агента (что `guard.mjs` и сканер секретов реально останавливают) - это часть 1 выше, `07-безопасность.md` (раздел 4.2) только сводит их в одну картину и называет три места, которые **не** проверяются ничем, кроме дисциплины:

| Граница | Чем проверить нельзя |
|---|---|
| Подключение PostgreSQL MCP к боевой, а не локальной базе разработки | ни один hook не читает `DATABASE_URL`, переданный инструменту - это решает только то, какую строку владелец проекта туда положит |
| Персональные данные покупателя, вставленные прямо в чат | ни один hook не читает содержимое сообщений |
| Юридический или медицинский текст, опубликованный без проверки смысла | ни сканер, ни линтер не читают смысл текста |

Эти три строки честно остаются «проверить нечем» - это границы доверия, а не программы (`CLAUDE.md`: «hook - страховка от ошибок агента, а не граница безопасности»).

### 3.2 Адресация заказа - по `cuid`, не по сквозному номеру

| | |
|---|---|
| **Что проверяем** | страница `/thanks/[orderId]` и любой запрос статуса заказа принимают только `cuid` (`Order.id`); по сквозному номеру (`Order.number`) заказ извне не находится |
| **Как запускаем** | тест маршрута `app/thanks/[orderId]/page.test.tsx` (или `app/api/orders/[id]/status/route.test.ts`) - запрос с подряд идущими числами `1043`, `1044` вместо `id` должен получить «не найдено», а не чужой заказ |
| **Ожидаемый результат** | подбор по номеру не возвращает ни одного чужого заказа ни на одном маршруте |
| **Что считаем ошибкой** | по числовому `number` вместо `cuid` удалось получить контакты или сумму чужого заказа |

### 3.3 Ограничение частоты проверки промокода

| | |
|---|---|
| **Что проверяем** | не больше **20 попыток проверки кода в минуту с одного IP или сессии**; при превышении - отказ «слишком часто», не «код неверный» |
| **Как запускаем** | тест `app/api/promo-code/route.test.ts` - 21 запрос подряд с одного адреса за минуту |
| **Ожидаемый результат** | первые 20 запросов обрабатываются как обычно, 21-й получает отказ по частоте, а не по содержимому кода |
| **Что считаем ошибкой** | 21-й и последующие запросы всё ещё возвращают `valid`/`invalid`, а не отказ по частоте; либо текст отказа выдаёт, что сработал именно лимит, а не «код не найден» (что подсказывает атакующему разницу ответов) |

### 3.4 Ссылка на экран отгрузки - короткий срок, одно действие

| | |
|---|---|
| **Что проверяем** | подписанный токен (`SHIPPING_LINK_SECRET`) действует **15 минут** и даёт право ровно на одно действие - открыть карточку одного заказа и проставить трек-номер |
| **Как запускаем** | `lib/shipping/token.test.ts` - выпустить токен, проверить сразу (проходит), подделать время истечения на 16-ю минуту (отклоняется), передать токен для другого `orderId` (отклоняется) |
| **Ожидаемый результат** | токен старше 15 минут или выпущенный для другого заказа отклоняется страницей `/shipping/[token]` с «ссылка недействительна» |
| **Что считаем ошибкой** | токен принят после истечения срока или дал доступ к заказу, для которого не выпускался |
| **Проверить нечем** | токен не отмечается использованным в базе (осознанный компромисс `07-безопасность.md`, 4.3) - значит нельзя автоматически проверить «использован ровно один раз», только срок действия |
| ⚠️ | этот экран пишется только при подтверждении вопроса 2.3 в `../ВОПРОСЫ.md`; без подтверждения `app/shipping/` и `lib/shipping/` не появляются вовсе |

## Часть 4. Смертельные риски чертежа (`09-риски.md`)

Из десяти причин премортема четыре названы смертельными. Ниже - какие из них вообще сводятся к автоматической проверке, а какие честно нет.

### 4.1 Причина 4 - маркировка «Честный знак»: гейт перед первым платежом

Это единственная из четырёх смертельных причин, которая превращена в жёсткий блокер приёмки (`01-что-строим.md`, раздел 6, пункт 9; `09-риски.md`, причина 4).

| | |
|---|---|

## Часть 7. Что нельзя проверить автоматически - честный список

Собрано из частей 2-4, чтобы не потерять среди таблиц:

1. **Происхождение цифры на экране** (2.2) - линтер ловит литерал в коде, не то, что цифра действительно пришла из базы.
2. **Медицинские обещания и фальшивые зачёркнутые цены** (`00-правила-проекта.md`, «Запрещено») - вопрос смысла текста, а не структуры данных. ⚠️ Если владелец захочет частичную защиту - список запрещённых слов (`лечит`, `вылечит`, `гарантированно`, `беременн`) как отдельный скрипт-помощник по аналогии с `check_secrets.py`, не решение, а предложение.
3. **Границы доверия агента** (3.1) - боевая база в PostgreSQL MCP, персональные данные в переписке, публикация юридических текстов без проверки смысла.
4. **Аварийный план и резервный контакт** (4.3) - можно проверить, что документ существует, нельзя проверить, что он верный, и нельзя проверить, что резервный контакт назначен.
5. **Честность формулировки про атрибуцию Ozon/WB** (4.4) - правка текста документа, не поведение кода.
6. **Использование ссылки на экран отгрузки ровно один раз** (3.4) - защита только сроком действия, не отметкой об использовании.
7. **«Инфраструктура/CloudPayments не останавливаются автоматически при перерасходе»** (часть 3.5) - это отсутствие действия, а не действие; тест может подтвердить, что сигнал появился, но не может доказать, что нигде в коде намеренно нет автостопа.

## Журнал решений

1. **Документ пересобран вокруг четырёх источников, которые назвал владелец** (сценарии приёмки из шага 10, нерушимые правила из шага 00, права и потолки из шага 07, смертельные риски из шага 09), а не переписан заново с нуля - процессные проверки часть 1 не изменились с прошлой версии, потому что код защит с 12.09.2026 не менялся.
2. **Сценарии приёмки (часть 5) собраны как перекрёстная ссылка на уже описанные проверки, а не как отдельный список** - потому что все девять условий приёмки и так по отдельности разобраны правилами шага 00 и разделами шага 07; повторять их текстом второй раз значило бы держать два места, которые могут разойтись.
3. **Из четырёх смертельных рисков шага 09 только один (маркировка) превращён в жёсткий блокер кода** - остальные три (недоступность разработчика, cookie-атрибуция, атрибуция маркетплейсов) либо организационные, либо уже закрыты правкой текста в других шагах, а не кодом, и это названо прямо, а не выдано за проверку.
4. **Денежные потолки выделены в отдельную часть 3.5**, а не растворены среди прав - потому что это не про то, что агенту нельзя, а про то, что продукт обязан сам себя останавливать, и раньше эта тема ни разу не собиралась в одном месте.

**Решение: список автоматических проверок собран не пересказом четырёх исходных документов подряд, а разбором каждого правила, риска и условия приёмки на вопрос «это вообще можно проверить кодом?» - там, где да, показано действие-результат-инструмент с именем будущего файла теста по карте `08-структура-кода.md`; там, где нет (медицинские тексты, происхождение цифры на экране, аварийный план, честность формулировки про Ozon), написано «проверить нечем» прямо, а не придуман тест, который создавал бы ложное чувство защиты - и именно поэтому из четырёх смертельных причин шага 09 в проверки вошла ровно одна, маркировка, потому что только она действительно блокируется кодом, а не человеческой дисциплиной.**
